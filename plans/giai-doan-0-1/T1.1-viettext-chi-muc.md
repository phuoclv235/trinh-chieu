# T1.1 `VietText` và `LibraryIndex`

**Model:** Opus 5.5 · **Phụ thuộc:** T0.5 · **Ước lượng:** 3 ngày · **Chạy:** Linux

## Phần 1: `VietText`

```swift
public enum VietText {
    /// Gộp để so khớp: NFD, bỏ dấu kết hợp U+0300–U+036F, đ/Đ → d, chữ thường, gộp khoảng trắng liên tiếp thành một, bỏ khoảng trắng đầu cuối.
    public static func fold(_ s: String) -> String
    /// Như fold nhưng bỏ luôn dấu câu và gạch nối: "Sáng-thế Ký" → "sang the ky".
    public static func foldLoose(_ s: String) -> String
    /// Chuẩn hoá lưu trữ: NFC, thay CRLF/CR bằng LF, bỏ ký tự điều khiển trừ LF và TAB, bỏ BOM.
    public static func normalize(_ s: String) -> String
    /// Chia truy vấn thành các từ đã fold, bỏ từ rỗng.
    public static func queryTerms(_ s: String) -> [String]
}
```

Lưu ý: bộ bỏ dấu sẵn của SQLite (`remove_diacritics`) không đổi "đ" thành "d", nên **không** dùng nó; luôn gộp bằng `VietText.fold` trước khi đưa vào chỉ mục và trước khi truy vấn.

Test bắt buộc: "Nguyễn" → "nguyen"; "ĐẤNG" → "dang"; "Giăng 3:16" → "giang 3:16"; chuỗi NFD và NFC cùng cho một kết quả; chữ "ư", "ơ", "ă", "â", "ê", "ô" đều về chữ gốc; tiếng Anh giữ nguyên chữ thường; 10.000 chuỗi ngẫu nhiên không làm hỏng (không crash, kết quả chỉ chứa ASCII khi đầu vào là tiếng Việt và ASCII).

## Phần 2: `LibraryIndex`

### Chọn lớp truy cập SQLite

1. Thêm GRDB (bản 7.x mới nhất) vào `Package.swift`, chỉ cho target `LibraryIndex` và `Scripture`.
2. Kiểm trên CI Linux (`core.yml`): build và chạy một test tạo bảng FTS5. Container cần `libsqlite3-dev`; thêm bước cài vào `core.yml` nếu image chưa có.
3. **Nếu GRDB không build hoặc FTS5 không chạy trên Linux:** bỏ GRDB, viết lớp bọc mỏng `SQLiteDB` (mở, `execute`, `prepare`, gắn tham số, đọc dòng, giao dịch; dưới 400 dòng) trên module hệ thống `SQLite3` (Mac) và `CSQLite` (Linux, `systemLibrary` target trỏ `sqlite3`). Ghi quyết định vào mô tả PR. Không thử thư viện thứ ba khác.

### API

```swift
public actor LibraryIndex {
    public init(databaseURL: URL) throws                 // tạo hoặc mở; indexVersion khác thì xoá và dựng lại
    public func upsert(_ entries: [IndexEntry]) throws   // trong một giao dịch
    public func remove(ids: [String]) throws
    public func removeAll(kind: IndexKind) throws
    public func search(_ query: String, kinds: Set<IndexKind>, limit: Int = 50) throws -> [SearchHit]
    public func count(kind: IndexKind) throws -> Int
}

public enum IndexKind: String, Sendable, CaseIterable { case presentation, theme, plan, media, verse }

public struct IndexEntry: Sendable, Equatable {
    public var id: String, kind: IndexKind, title: String, subtitle: String?, body: String?, path: String?, modifiedAt: Date?
}

public struct SearchHit: Sendable, Equatable {
    public var id: String, kind: IndexKind, title: String, subtitle: String?, score: Double
}
```

Lược đồ đúng như `docs/dinh-dang-tep.md` mục 6. `IndexEntry` chưa gộp dấu; `LibraryIndex` tự gộp khi ghi cột `*_f`.

### Quy tắc tìm

- Truy vấn rỗng: trả rỗng.
- Mỗi từ của `VietText.queryTerms` thành `"<từ>"*`, nối bằng khoảng trắng (AND). Thoát dấu ngoặc kép trong từ.
- Truy vấn toàn chữ số (ví dụ "123"): ngoài FTS, cộng thêm các mục có `subtitle` bắt đầu bằng số đó (tìm theo số thánh ca), xếp trên cùng.
- Xếp hạng `bm25(items_fts, 10.0, 5.0, 1.0)`, rồi `title` theo thứ tự chữ cái.
- Phần "câu Kinh Thánh" có thể tới khoảng 31.000 mục mỗi bản dịch: `search` với `kinds` không chứa `.verse` không được chậm đi vì chúng.

### Hiệu năng (đo trên Linux CI, ghi vào PR)

- Chèn 5.000 bài hát và 31.102 câu: dưới 5 giây.
- Một truy vấn 2 từ trên dữ liệu đó: dưới 20 ms, p95 của 100 lần.

## Tiêu chí nghiệm thu

1. Gõ "chua la da" tìm ra "Chúa Là Đá Muôn Đời"; "dang" ra "Đấng"; "123" ra thánh ca số 123 đứng đầu.
2. Xoá tệp chỉ mục rồi mở lại: tự tạo lại lược đồ, không lỗi.
3. Đổi `indexVersion`: dữ liệu cũ bị xoá, bảng tạo lại.
4. Đạt hai số đo hiệu năng.
5. Test chạy lặp 3 lần xanh trên Linux.
